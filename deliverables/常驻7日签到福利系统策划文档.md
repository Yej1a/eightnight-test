# 常驻 7 日签到福利系统策划文档

## 1. 文档说明

### 1.1 背景

项目计划在现有线上项目中新增一个常驻七日签到福利系统。玩家每天登录游戏后可领取当日签到奖励，累计完成 7 个签到槽位后获得阶段大奖。系统长期开放，作为稳定的留存与活跃补充模块存在。

### 1.2 文档目标

本文档用于沉淀该功能的完整规则，覆盖：

- 核心玩法规则
- 前端入口与页面表现
- 后端状态、接口与发奖逻辑
- 运营可配置内容
- 开发实现时必须考虑的特殊状态与边界情况
- 功能测试与验收口径

### 1.3 适用前提

- 默认项目已具备登录、角色、背包、邮件、活动配置与基础发奖能力
- 本方案为常驻福利系统，不是一次性新手 7 日签到
- 本方案面向全量玩家开放，不设置等级或章节门槛
- 默认以“区服内角色维度”参与签到，同账号下不同角色、不同区服互不共享进度

## 2. 功能目标

### 2.1 业务目标

- 提升玩家日常登录活跃
- 提供长期稳定的轻量福利抓手
- 通过补签设计增加一定的付费转化空间

### 2.2 用户目标

- 玩家能明确知道今天是否可领奖励
- 漏签后不会因断签直接损失整轮进度
- 奖励获取路径清晰，补签成本透明

## 3. 核心规则

### 3.1 基础规则总览

- 每轮签到包含 7 个签到槽位
- 玩家在每个服务器日最多获得 1 个新的免费签到机会
- 玩家正常签到后可领取对应槽位奖励
- 若当天未领取，次日该槽位转为可补签状态
- 漏签不会清空整轮进度
- 玩家可消耗钻石对历史漏签槽位进行补签
- 第 7 个槽位开启后，只代表最后一个日奖励槽位开放，不代表阶段大奖可直接领取
- 阶段大奖必须在本轮 7 个槽位全部完成签到后才可领取，正常签到与补签都计入“全部签到”
- 单轮完成后当日不立刻开启新一轮，下一次日切后再进入下一轮
- 系统长期开放，7 天完成后循环进入下一轮

### 3.2 日切规则

- 统一使用服务器时区
- 每日 `00:00` 日切
- 日切后刷新当轮签到状态
- 日切时不补发中间遗漏的免费签到次数
- 硬规则：玩家未登录期间也按日切规则照常推进开槽，但单轮最多推进到第 7 个槽位；回归时，所有已开放但未领取的历史槽位统一转为可补签状态

### 3.3 轮次规则

- 玩家首次进入系统时初始化当前轮次为第 1 轮
- 单轮最多只开放 7 个槽位
- 单轮完成前，每次日切至多新增 1 个新槽位
- 单轮完成后，页面状态显示“本轮已完成”
- 本轮完成但阶段大奖未主动领取时，不阻塞下一轮开启；系统在下一次日切开启新一轮前自动补发阶段大奖
- 下一次日切后自动进入下一轮，并开放下一轮的第 1 个槽位

### 3.4 签到与补签规则

#### 正常签到

- 仅当存在“今日可签到”槽位时可执行
- 每个自然日仅能正常签到 1 次
- 正常签到不消耗资源

#### 补签

- 仅针对历史未领取且已开放的槽位生效
- 补签需消耗钻石
- 每个漏签槽位最多补签 1 次
- 补签与正常签到互不冲突，同一天可先正常签到，再补签历史槽位

### 3.5 奖励规则

- 每个槽位绑定一份日奖励
- 第 7 个槽位奖励与阶段大奖是两笔独立奖励
- 阶段大奖不能因“到达第 7 天”直接领取，必须等本轮 7 个槽位全部签到完成后才开启领取资格
- 若第 7 天已开启，但玩家仍有历史漏签槽位未补签，则阶段大奖保持锁定
- 当最后一个未完成槽位被正常签到或补签完成后，阶段大奖状态变为可领取
- 若阶段大奖在本轮完成当日未被主动领取，系统需在下一轮开启前自动补发，避免玩家因忘领而损失奖励
- 活动关闭时，所有已满足大奖领取资格但未领取的玩家，系统需在关闭结算时自动补发阶段大奖
- 日奖励与阶段大奖均应生成唯一发奖流水

### 3.6 参与范围与配置生效规则

- 默认按“角色 ID + 区服 ID + 活动 ID”作为签到唯一参与维度
- 同账号下不同角色互不共享签到进度、补签次数与大奖资格
- 奖励组、阶段大奖、补签价格、发奖策略按“轮次快照”冻结
- 玩家进入某一轮后，该轮配置不因运营热更而改变
- 运营热更后的奖励、价格与投放分组，默认仅对新开启轮次生效
- 前台文案、资源图、说明文字可热更，但不得改变当前轮次的结算结果

## 4. 槽位状态设计

### 4.1 槽位状态枚举

| 状态值 | 状态名称 | 说明 |
| --- | --- | --- |
| `locked` | 未解锁 | 未来槽位，尚未到开放日期 |
| `claimable` | 可签到 | 当日正常可领取的免费槽位 |
| `claimed` | 已签到 | 通过正常签到完成领取 |
| `makeup_claimable` | 可补签 | 历史已开放但未领取，可消耗钻石补领 |
| `makeup_claimed` | 已补签 | 通过补签完成领取 |

### 4.2 单轮状态流转

1. 活动开启后，玩家首次访问时初始化第 1 轮
2. 第 1 个槽位开放为 `claimable`
3. 玩家当日点击签到后，槽位变为 `claimed`
4. 若当天未领，次日日切后该槽位变为 `makeup_claimable`
5. 新的一天开放下一个槽位为 `claimable`
6. 当 7 个槽位全部被正常签到或补签完成后，轮次状态变为 `completed`，阶段大奖状态变为 `claimable`
7. 阶段大奖主动领取完成或系统自动补发完成后，当天停留在本轮完成态，下一次日切后初始化下一轮第 1 个槽位

### 4.3 玩家轮次状态

| 字段 | 含义 |
| --- | --- |
| `currentRoundNo` | 当前轮次编号 |
| `roundStartDate` | 当前轮次开始日期 |
| `roundStatus` | 当前轮次状态：`in_progress` / `completed` |
| `todayClaimed` | 玩家今日是否已执行正常签到 |
| `lastRefreshDate` | 上一次按日切刷新状态的日期 |
| `grandRewardStatus` | 本轮大奖状态：`locked` / `claimable` / `claimed` |
| `roleId` | 角色 ID |
| `serverId` | 区服 ID |
| `roundConfigVersion` | 当前轮次配置快照版本 |
| `settlementStatus` | 结算状态：`normal` / `pending_compensation` |

## 5. 前端表现与交互规则

### 5.1 入口设计

- 功能入口常驻在福利页或活动集合页
- 若项目已有大厅福利 Icon，可同步增加入口映射
- 红点仅在“存在免费可签到槽位”时展示
- 特例：若第 7 天已开启，且玩家只差补签历史漏签槽位即可解锁阶段大奖，且当前钻石余额足以完成所需补签，可显示红点提示
- 其他情况下，存在仅可补签但无免费可领时，不显示红点
- 阶段大奖已处于 `claimable` 但未领取时，入口持续显示红点，直到玩家主动领取或系统自动补发完成

### 5.2 页面展示内容

签到面板需展示以下信息：

- 当前轮次
- 7 个签到槽位奖励
- 当前完成进度
- 第 7 天奖励及阶段大奖
- 阶段大奖当前状态：未解锁、可领取、已领取
- 当前可补签槽位数
- 单次补签钻石消耗
- 活动说明与规则提示

### 5.3 槽位展示规则

- 当前可免费领取的槽位显示主按钮“签到领取”
- 历史漏签槽位显示“补签”按钮及消耗价格
- 已签到/已补签槽位显示已完成态
- 未解锁槽位显示未开放态
- 第 7 槽位或大奖区域应有明显视觉强化
- 阶段大奖在未满足 7 槽全部完成前显示锁定态，并明确标注“补签剩余槽位后可领取”

### 5.4 页面主状态

| 页面状态 | 触发条件 | 页面表现 |
| --- | --- | --- |
| 未开启 | 活动未到开启时间 | 显示未开启说明，不可操作 |
| 进行中且今日可签到 | 存在 `claimable` 槽位 | 高亮签到按钮，入口显示红点 |
| 进行中但今日已签且存在可补签 | 无 `claimable`，有 `makeup_claimable` | 展示补签按钮，不显示红点 |
| 第 7 天已开启且大奖待补签解锁 | 第 7 槽位已开放，阶段大奖仍锁定，且存在历史 `makeup_claimable` | 展示大奖锁定原因；仅当钻石余额足够完成剩余补签时显示红点提示 |
| 进行中且等待下一日 | 无 `claimable`，无 `makeup_claimable`，轮次未完成 | 展示进度和下一次开放提示 |
| 本轮完成待领大奖 | 本轮 7 槽全部领取，阶段大奖为 `claimable` | 展示大奖领取按钮 |
| 本轮完成 | 本轮 7 槽全部领取，阶段大奖已领取 | 展示完成态和大奖已领取状态 |
| 已关闭 | 活动关闭 | 前台不可继续操作 |

### 5.5 交互要求

- 点击签到前前端可做基础可用性校验，但最终以服务端结果为准
- 签到、补签按钮提交后需进入防重复点击状态
- 接口返回成功后立即刷新当前状态与奖励展示
- 若奖励走邮件补发，前端需明确提示“奖励已通过邮件发送”

## 6. 后端对象与接口设计

### 6.1 核心配置对象

| `makeupCostValue` | 单次补签价格 |
| `unlockRule` | 开放规则，默认全量玩家 |
| `deliveryPolicy` | 发奖策略，优先背包，失败走邮件 |
| `redPointPolicy` | 红点策略：免费可签到时显示；大奖待领取或满足特例条件时可提示 |

| `roundConfigFreezePolicy` | 当前轮次配置冻结策略 |

#### 扩展运营配置

- 奖励组版本号
- 生效区服/玩家分组
- 是否允许活动重开后继承历史进度
- 是否启用轮次奖励轮换
- 前台文案、角标、公告资源引用
- 是否允许 GM/运营手动重置轮次
- 是否允许关闭时自动补签或仅自动补发大奖

### 6.3 接口设计

#### `GET /signin/status`

用途：

- 查询活动当前状态与玩家签到状态

返回至少包含：

- 活动是否开启
- 当前轮次
- 7 个槽位状态
- 今日是否可正常签到
- 可补签槽位列表
- 补签价格
- 当前钻石余额是否足够完成剩余补签
- 阶段大奖状态与锁定原因
- 红点状态
- 当前轮次配置版本

#### `POST /signin/claim`

用途：

- 处理当前当日免费签到

约束：

- 仅允许处理当前 `claimable` 槽位
- 必须幂等
- 重复点击只能成功一次
- 成功后返回最新状态及发奖结果

#### `POST /signin/makeup`

用途：

- 处理历史漏签补签

入参：

- `slotIndex`

执行顺序：

1. 校验活动开启状态
2. 校验槽位是否可补签
3. 校验玩家钻石余额
4. 生成补签订单与扣费流水
5. 扣除钻石
6. 发放对应槽位奖励
7. 若补签后满足 7 槽全部完成，则将阶段大奖状态改为 `claimable`
8. 更新玩家状态并写入流水

约束：

- 不能出现已扣费但状态未记录且不可恢复的情况
- 同一槽位不能重复补签
- 若扣费成功后奖励发放与邮件补发都失败，需将玩家结算状态置为 `pending_compensation`，由补偿任务异步完成

#### `POST /signin/grand-reward/claim`

用途：

- 领取本轮阶段大奖

约束：

- 仅当本轮 7 个槽位全部完成，且 `grandRewardStatus = claimable` 时可领取
- 必须幂等
- 重复点击只能成功一次
- 成功后返回最新大奖状态与发奖结果
- 若发放失败，需进入补偿队列，禁止玩家重复消耗资格

#### `GET /signin/records`

用途：

- 用于客服、运营与问题排查查看玩家轮次与奖励流水

返回至少包含：

- 玩家当前轮次
- 每个槽位领取方式与时间
- 阶段大奖领取状态与领取时间
- 当前轮次配置版本与生效奖励组
- 补签扣费流水与补偿任务状态
- 奖励发放记录
- 邮件补发记录

## 7. 奖励发放与一致性策略

### 7.1 发奖优先级

- 优先尝试直发背包
- 背包发放失败时走邮件补发
- 邮件标题、来源与内容需带签到系统标识，避免和其他运营活动混淆
- 若直发背包与邮件补发都失败，必须创建补偿任务并保留完整订单、扣费与发奖上下文

### 7.2 发奖流水

- 每次日奖励发放生成唯一流水号
- 阶段大奖发放生成独立流水号
- 每次补签扣费生成独立订单号与货币流水号
- 自动补发阶段大奖也生成独立补偿流水号
- 所有流水支持按玩家、轮次、槽位检索

### 7.3 一致性要求

- `claim` 与 `makeup` 接口均需保证幂等
- `grand-reward/claim` 接口需保证幂等
- 多端同时点击时，仅允许一个请求成功修改状态
- 槽位奖励发放成功后，只能改变阶段大奖资格，不直接等价为阶段大奖已发放
- 若阶段大奖领取时发放失败，系统需具备自动补偿能力
- 已发放成功的日奖励不可因后续阶段大奖失败而回滚
- 补签扣费成功后，任何发奖链路失败都不得丢失订单上下文
- 同一补偿任务必须幂等执行，避免重复补奖

## 8. 运营能力设计

### 8.1 必需运营能力

- 活动开关配置
- 活动时间配置
- 日奖励与阶段大奖配置
- 补签价格配置
- 区服/分组投放配置
- 前台文案与资源位配置
- 玩家状态与发奖流水查询
- 手动补发能力
- 补偿任务查询与重试能力
- GM/客服轮次重置、大奖状态修复、槽位修复能力

### 8.2 奖励组切换规则

- 奖励组默认对新开启轮次生效
- 已经开始的轮次不追溯修改
- 若需要强制让旧轮次切换新奖励组，必须通过运营重置配置或专门干预流程处理

### 8.3 热更与后台干预规则

- 奖励组、大奖内容、补签价格、发奖策略均按轮次快照冻结
- 正在进行中的轮次不允许直接热更为另一套奖励或价格
- GM/客服手动重置轮次时，必须写审计日志，并在玩家下一次请求前清理旧缓存
- 后台补发、修复状态与玩家前台请求并发时，以服务端串行锁保证顺序一致

## 9. 特殊状态与边界情况

以下内容为开发实现时必须显式处理的边界与异常。

### 9.1 跨日未领取

- 玩家登录后未点击签到，跨日后原当日槽位转为 `makeup_claimable`
- 新的一天仅新增 1 个新的 `claimable` 槽位
- 不允许系统把漏掉的天数自动按免费签到补齐

### 9.2 当日已签到但历史有漏签

- 玩家当天已正常签到后，不能再次正常签到
- 但仍可对历史 `makeup_claimable` 槽位执行补签

### 9.3 同一槽位重复操作

- 已领取槽位不能再次签到
- 已补签槽位不能再次补签
- 同一槽位不允许同时被两个请求重复消费

### 9.4 并发与重复点击

- 多端同时点击签到，只允许一次成功
- 断线重试、重复请求、前端重复提交都必须被幂等拦截
- 服务端应以玩家状态锁或等价机制保证单玩家串行更新

### 9.5 第 7 槽位结算

- 第 7 槽位可由正常签到或补签触发完成
- 第 7 天开启仅代表最后一个日奖励槽位开放，不直接等于阶段大奖可领取
- 只有 7 个槽位全部完成后，阶段大奖才变为可领取
- 若第 7 天已开启且只差补签历史漏签槽位即可解锁阶段大奖，且当前钻石余额足以完成剩余补签，可显示红点提示玩家补齐
- 阶段大奖领取失败时，需记录补偿任务，不影响已到账的日奖励

### 9.6 发奖失败

- 背包满、道具类型异常、接口超时等情况统一走邮件补发
- 走邮件补发后，系统仍视为本次奖励发放成功
- 邮件补发状态需写入玩家记录，供客服核查

### 9.7 活动关闭

- 活动关闭后，不再允许新增正常签到与补签
- 已发送到邮件中的奖励仍按邮件系统的生命周期领取
- 活动重开是否继承历史进度，应以运营配置为准
- 对于已满足阶段大奖资格但未领取的玩家，活动关闭结算时自动补发阶段大奖

### 9.8 日切瞬间请求

- 请求到达与最终落库跨越 `00:00` 时，以服务端最终校验结果为准
- 若玩家资格因跨日发生变化，请求需重新判定当前可操作槽位
- 不允许使用前端缓存状态直接作为结算依据

### 9.9 长时间未登录

- 玩家长时间未登录后回归，不自动补发中间所有天数的免费奖励
- 玩家未登录期间，系统仍按日切规则每天推进 1 个新槽位开放，单轮最多推进到第 7 槽
- 回归时，当前轮次中所有已开放未领取的槽位统一转为可补签状态
- 不因为未登录而额外补发免费签到次数

### 9.10 阶段大奖已可领取但未领取

- 阶段大奖进入 `claimable` 后，玩家可主动领取
- 若玩家当日未主动领取，不阻塞下一轮开启
- 系统在下一次日切前自动尝试补发阶段大奖，成功后将状态改为 `claimed`
- 若自动补发失败，需进入补偿队列；在补偿完成前不得重复生成下一笔大奖

### 9.11 补签扣费成功但下游发奖失败

- 补签扣费成功后，若背包发奖失败且邮件补发也失败，不允许把该次补签视为完成
- 系统需将本次操作标记为 `pending_compensation`
- 补偿任务完成后，才能最终将槽位状态和奖励到账状态视为成功闭环
- 客服后台必须可按订单号查询该次异常链路

### 9.12 配置热更与轮次快照

- 玩家进入当前轮次时，系统需固化该轮的奖励组、阶段大奖、补签价格与发奖策略
- 运营在活动期间热更配置，只影响后续新开启轮次
- 若确需影响当前轮次，必须通过“重置轮次/重置活动”的运营手段显式执行，不能静默覆盖

### 9.13 账号、角色、区服归属

- 默认按角色+区服维度参与签到
- 同账号切换角色、切换区服时，不共享当前轮次、补签资格与阶段大奖状态
- 若项目未来支持合服、转服或角色迁移，需在迁移方案中明确是否继承签到进度；本版默认不自动合并

### 9.14 后台干预并发

- GM/客服执行补发、重置轮次、修复大奖状态时，必须与玩家前台请求串行化
- 后台干预写入后需刷新玩家签到缓存，避免前台读取旧状态再次提交
- 所有后台干预都必须保留操作者、时间、原因与影响范围审计记录

### 9.15 红点资格与余额不足

- 免费签到红点不依赖货币余额
- “补签即可解锁阶段大奖”的特例红点，默认要求玩家当前钻石余额足以覆盖剩余补签总价
- 若余额不足，不在入口给强提醒，但进入面板后需展示“补签后可解锁大奖”与当前差额

### 9.16 客户端缓存与旧版本请求

- 所有领奖、补签、领大奖资格以服务端实时校验为准
- 若客户端缓存的活动配置版本与服务端不一致，服务端应返回最新状态并要求前端刷新
- 前端不得基于本地缓存直接推导“大奖是否可领”或“补签价格”

- 补签成功

- 阶段大奖领取成功
- 阶段大奖自动补发成功
- 补签扣费后进入补偿队列
- 红点曝光与点击拆分统计

### 10.2 关注指标

- 正常签到成功率
- 补签点击率
- 补签付费转化率
- 单轮完成率

- 阶段大奖自动补发率

- 分区服/分组转化差异

## 11. 测试与验收

### 11.1 功能验收场景

1. 新玩家首次进入系统，正确初始化第 1 轮第 1 槽位
2. 连续 7 天每日签到，正确发放 7 次日奖励，并获得 1 次阶段大奖领取资格；主动领取后奖励到账
3. 单轮完成后，当天保持完成态，下一次日切后才进入下一轮
4. 漏签 1 天后继续登录，历史槽位转为可补签，当前天槽位可正常签到
5. 同一天先正常签到，再补签历史槽位，两类操作都成功且状态正确
6. 多个历史漏签槽位在同一天连续补签，扣费与发奖结果一致
7. 第 7 槽位开启但历史仍有漏签时，阶段大奖保持锁定且不允许领取
8. 通过补签补齐最后一个漏签槽位后，阶段大奖状态正确变为可领取
9. 第 7 天已开启且只差补签即可解锁阶段大奖时，红点提示符合规则
10. 阶段大奖领取成功后不可重复领取
11. 背包满时奖励正确改走邮件，不丢失不重复
12. 多端并发点击同一签到按钮，仅一个请求成功
13. 多端并发领取阶段大奖时，仅一个请求成功
14. 日切前后请求边界正确，不出现旧状态污染
15. 阶段大奖已可领取但未主动领取时，次日日切前自动补发成功，且不阻塞新轮次开启
16. 活动关闭后不可继续签到、补签或主动领取阶段大奖；已满足资格未领取的阶段大奖被自动补发
17. 奖励组与补签价格热更后，仅新轮次使用新配置，进行中轮次保持快照不变
18. 同账号切换角色或区服时，不串用签到进度
19. 补签扣费成功但背包与邮件都失败时，正确进入补偿队列，后续补偿成功且不重复到账
20. GM/客服后台重置轮次或补发奖励时，不与玩家前台请求产生重复结算

### 11.2 非功能关注点

- 并发下状态一致性
- 发奖失败补偿能力
- 数据记录可追溯性
- 埋点字段完整性

## 12. 默认取值与二期预留

### 12.1 当前版本默认取值

- 补签价格为固定单价
- 红点默认提示免费签到；第 7 天已开启且只差补签即可解锁阶段大奖，且当前余额足以补齐时，也可提示
- 大奖为第 7 天奖励外额外附加奖励
- 奖励组默认按轮次复用
- 默认按角色+区服维度参与
- 大奖已可领取但未领取时，默认在下一次日切开启新轮次前自动补发

### 12.2 暂不纳入本版范围

- 阶梯补签价格
- 新手专属签到版本
- 排行榜、分享裂变、任务联动
- 本地时区日切
- 自动签到

## 13. 实现摘要

如果该文档交给开发落地，可按以下顺序拆解：

1. 先实现活动配置、玩家状态与槽位状态模型
2. 再实现日切刷新、正常签到、补签与大奖发放流程
3. 接着补齐前端入口、红点与面板状态
4. 最后补齐运营配置页、查询能力、埋点与补偿机制

该方案的最小正确目标不是“尽快做出一个能领奖励的页面”，而是“做出一个规则闭合、状态一致、线上可长期运营的常驻签到系统”。
